# 평가 (Evaluation)

## 무엇을 재는가

주장: **렌더링 전에 에이전트가 필요한 것만 묻고 사용자가 답하면, 적은 비용으로 사용자 의도에 맞는 결과가 나온다.**

| 조건 | 내용 | 측정 방법 |
|---|---|---|
| `auto` (확인 없음) | 에이전트의 첫 계획을 그대로 실행 | 자동 (`scripts/run_eval.py`) |
| `negotiated` (협상) | 같은 첫 계획 → 질문에 답 + 명세서 검토 후 클릭으로 수정 | 자동: 정답을 아는 가상 사용자 (상한값) |
| 텍스트만 vs 텍스트+화면 | 같은 협상, 박스 표시 유무 | **사용자 실험** (`?mode=text`) |

두 자동 조건은 **같은 모델 응답 1회**를 공유하므로, 차이는 순수하게 협상의 효과다.
가상 사용자는 클릭만 하고 AI를 다시 부르지 않는다 (코드에서 강제).

## 지표

| 지표 | 의미 |
|---|---|
| success | 모든 작업이 순서대로, 맞는 종류로, 노출/과잉 0.25초 이하 |
| **missed s** | 가려야 할 사람이 화면에 **노출된 시간(초)** — 프라이버시 실패 |
| extra s | 건드리면 안 되는 사람이 가려진 시간(초) |
| questions/task | 에이전트가 물은 질문 수 |
| **needless questions** | 에이전트가 이미 맞혔는데 물은 질문 수 — 협상의 낭비 |
| clicks/task | 사용자가 명세서를 보고 스스로 고친 클릭 수 |

얼굴/몸 구분은 채점하지 않는다 ("그 남자 블러"를 얼굴로 하든 몸 전체로 하든 정답). **누가, 언제** 가려지는지만 본다.

## 실행

```bash
cd backend
uv run python scripts/run_eval.py eval/crowd --max-usd 2      # Gemini
CUTPILOT_LLM_PROVIDER=offline uv run python scripts/run_eval.py eval/crowd   # 무료 리허설
```

결과: `outputs/eval/<set>-<시각>.md` (표), `.json` (과제별 전체 기록과 대화 로그).
응답은 캐시되므로 같은 과제를 다시 돌리면 비용 0, 같은 숫자.

과제 세트: `backend/eval/crowd/` — 샘플 군중 영상(20.6초, 사람 17명)에 대한 16개 과제(L1 3, L2 6, L3 4, L4 3).
추적 결과(`tracks.json`)를 고정해 두어 YOLO 버전이 바뀌어도 정답 id가 유지된다.

## 첫 결과 (2026-11-08, gemini-3.6-flash)

| level | condition | success | missed s | extra s | questions/task | needless q |
|---|---|---|---|---|---|---|
| L1 | auto / negotiated | 100% / 100% | 0 / 0 | 0 / 0 | 0 | 0 |
| L2 | auto / negotiated | 100% / 100% | 0 / 0 | 0 / 0 | 1.0 | 6 |
| L3 | auto / negotiated | 75% / 100% | 0 / 0 | 59.1 / 0 | 1.25 | 4 |
| L4 | auto / negotiated | 100% / 100% | 0 / 0 | 0 / 0 | 1.33 | 4 |
| **전체** | auto / negotiated | **94% / 100%** | 0 / 0 | 59.1 / 0 | 0.94 | **14 / 15** |

- 비용: 첫 실행 전체 **$0.077** (과제당 모델 호출 1~3회, 과제당 약 2~5초).
- L3-03 "가방 멘 사람 모자이크": 가방 든 사람이 여럿 → auto는 7명을 모자이크(59초 과잉), 협상은 질문 1번으로 해결.

### 발견

1. **Gemini의 지칭 인식(grounding)이 생각보다 강하다.** 외모로 한 명을 지칭한 L2 6개를 모두 맞혔다 (멀리 작게 보이는 사람 포함).
2. **그래서 질문 15개 중 14개가 불필요했다.** 대부분 "이 사람이 맞나요?"(confirm). → 확신이 높은 단일 매칭은 묻지 않고 명세서에서만 보여주는 쪽이 낫다는 근거. 다음 설계 결정 후보.
3. **협상이 값을 하는 곳은 진짜 모호할 때(L3)다.** 기여를 "항상 확인"이 아니라 "**모호할 때만** 묻고, 나머지는 명세서로"로 표현하는 것이 결과와 맞다.
4. 첫 실행에서 "회색 조끼 남자 모자이크"를 플래너가 **얼굴** 모자이크로 해석했는데 얼굴 트랙이 없어 아무도 가려지지 않았다. → 사람 박스 상단으로 얼굴 영역을 추정하는 임시 방법(`vision/heads.py`)을 넣어 해결. 실제 얼굴 검출기(YuNet)로 교체 예정.

### 한계 (보고 전에 반드시 해결/명시)

- **정답 라벨은 Claude가 프레임을 보고 붙였다.** 사람이 검수해야 한다 (`tasks.json`의 `labeled_by`).
- 영상 1개, 과제 16개 — 통계적으로 말할 수 있는 규모가 아니다. 영상 2~3개, 과제 40개 이상 권장.
- 과제가 쉽다. auto가 이미 94%라 협상의 이득을 보여주기에 천장이 낮다. **비슷한 옷차림, 겹침, 시간에 따라 바뀌는 지칭** 같은 어려운 과제를 늘려야 한다.
- 가상 사용자는 항상 정답을 알고 실수하지 않는다 → 실제 사용자 성능의 상한.
- 재실행 시 `calls/task`는 캐시 때문에 0으로 나온다. 비용·호출 수는 첫 실행 값을 쓴다.

## 사용자 실험 (텍스트만 vs 텍스트+화면)

같은 UI에서 `http://localhost:3000/?mode=text` 로 열면 미리보기의 박스가 숨겨진다 (헤더에 "텍스트 전용" 표시).

제안 프로토콜:
1. 참가자 10명 이상, 각자 두 조건 모두 수행 (순서 교차).
2. 과제는 `eval/crowd/tasks.json`의 L2~L4에서 조건별로 겹치지 않게 배정.
3. 기록: 완료 시간, 질문 수, 클릭 수, 최종 결과 → 같은 채점기로 missed/extra 계산 (세션 기록은 `GET /sessions/{id}`).
4. 끝나고 짧은 설문: 확신도, 부담감 (예: NASA-TLX 단축형).
